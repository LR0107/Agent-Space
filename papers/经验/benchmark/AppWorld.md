# AppWorld: A Controllable World of Apps and People for Benchmarking Interactive Coding Agents

**ACL 2024**

## 一、研究背景

随着大语言模型在指令理解、代码生成和工具调用方面能力增强，研究者希望让模型完成现实中的数字任务，例如：

- 根据备忘录中的购物清单购买商品；

- 从邮件中整理露营用品，再购买缺少的物品。

这类任务并不是简单地调用一次工具，而通常具有以下特点：

1. **需要操作多个应用；**
2. **后续操作依赖前面查询到的信息；**
3. **需要循环、条件判断、数据筛选等逻辑；**
4. **执行过程中可能遇到错误或意外情况；**
5. **既要完成目标，也要避免误操作。**

智能体需要的不只是“知道调用哪个 API”，而是要进行：

> 环境查询 → 理解返回结果 → 编写代码 → 执行代码 → 根据反馈继续调整。

### 以往评测基准存在的问题

论文认为，过去的工具调用基准过于简单，通常只要求模型按照较线性的顺序完成 **1—4 次 API 调用**。

这些基准主要有三个不足。

**第一，任务复杂度不够**

现实任务往往涉及多个应用、多次查询和复杂控制流程，而已有任务通常只是：

> 调用工具 A → 得到结果 → 调用工具 B → 输出答案。

它们很少要求模型编写包含循环、分支和数据处理的复杂代码。

**第二，缺少真正的环境交互**

很多任务可以仅根据题目直接生成一串调用步骤，不需要查看中间结果后再决定下一步。

但现实中，智能体往往必须先查看数据格式和内容，才能继续。例如，只有读取健身笔记后，模型才知道锻炼时间是按星期排列，进而决定如何提取当天信息。

**第三，评估方式不够可靠**

传统方法常把模型的操作步骤与一条“标准答案路径”比较。

但复杂任务可能有多种正确做法。例如，获取购物订单信息时，可以：

- 查询购物应用中的订单；
- 查看订单确认邮件；
- 查询下载的收据。

只要最终结果正确，都应该被视为成功。因此，仅比较操作步骤并不合理。

此外，智能体可能完成了目标，却同时造成额外破坏，例如：

- 下单成功，但误删了愿望清单；
- 批准了指定转账请求，却顺便批准了其他请求；
- 修改播放列表时误删了无关歌曲。

## 二、研究方法

### AppWorld Engine

AppWorld Engine 是一个模拟日常数字生活的执行环境。

系统实现了 9 个主要应用，覆盖多个日常领域，包括：

- Gmail：电子邮件；
- Amazon：购物；
- Venmo：转账；
- Spotify：音乐；
- SimpleNote：笔记；
- Todoist：待办事项；
- Phone：联系人和消息；
- Splitwise：费用分摊；
- FileSystem：本地文件系统。

这些应用共提供约 **457 个 API**，平均每个应用约 50 个 API。

**执行方式**

智能体在类似 Jupyter Notebook 的状态化执行环境中编写 Python 代码。

所谓“状态化”，是指：

- 前一次执行生成的变量可以在后面继续使用；
- 智能体可以分多轮写代码；
- 系统会返回执行结果和错误信息；
- 智能体根据结果继续修改代码。

模型既可以使用函数形式调用 API。

环境可控性

研究者可以控制：

- 数据库初始状态；
- 系统日期和时间；
- 用户账户和关系；
- 应用中的历史活动。

每次执行任务前，都能把环境恢复到相同的起点。这保证了不同模型和不同方法之间的比较是公平的。

系统可靠性

作者为 API 编写了大约：

- 1780 个单元测试；
- 3.4 万行测试代码；
- 98% 的代码覆盖率。

这样做是为了保证，无论智能体如何调用 API，环境都能给出一致且合理的反应。

**构建虚拟人物和数字生活数据**

AppWorld 中并不是空的应用，而是预先填充了大量模拟数据。

作者构造了 **106 名虚构人物**，年龄为 19—60 岁，他们具有：

- 不同的家庭和工作地址；
- 各个应用的账户；
- 朋友、家人、室友、同事等关系；
- 多年累积的邮件、转账、购物、音乐和笔记记录。

例如：

- 室友之间可能支付房租；
- 同事之间可能分摊拼车费用；
- 家人之间可能讨论旅行计划；
- 用户可能在过去两年里产生多次转账记录。

作者通过程序化方法生成大部分数据，对语义要求较高的内容进行人工编写，部分普通文本由 ChatGPT 辅助生成。最终数据库约有 **37 万行记录**。

**AppWorld 用数据库保存世界状态，用应用 API 作为操作入口，用业务逻辑模拟真实应用行为。**

Agent 不能直接修改数据库，而是调用模拟应用的 API，例如“发送邮件”“下单”“批准转账”。API 再按照真实应用逻辑更新底层数据库。

### **AppWorld Benchmark**

作者首先设计一个抽象的任务场景，然后从同一场景生成多个具体任务。

例如场景模板为：

> 我喜欢上一次在 Amazon 买的某种颜色的衣服，请购买相同款式和尺码。优先选择指定颜色；若没有，则选择原来的颜色。

其中“衣服类型”“购买颜色”等变量可以变化，从而生成不同任务。

每个任务生成器包含三部分：

1. **Setup：构建任务环境；**
2. **Evaluation：定义评估标准；**
3. **Validation Solution：编写可验证的正确解法。**

**任务设计的原则**

作者要求每个任务满足四项关键条件。

① 任务必须有明确解

任务指令中的前提必须成立。

例如，任务要求重新购买“上次买的 T 恤”，那么数据库中必须确实存在历史 T 恤订单。

② 加入干扰信息

系统会故意加入看似相关、实际无关的数据。

例如：

- 用户过去买过多件不同颜色、不同尺码的 T 恤；
- 邮箱里有多封相似主题的邮件；

这样可以防止模型通过简单关键词匹配完成任务。

③ 加入现实障碍

任务可能设置一些自然出现的问题，例如：

- 默认银行卡已经过期；
- 某种商品颜色缺货；
- 部分邮件没有回复；
- API 返回分页数据；
- 一次调用失败，需要采用其他方法。

这用于测试模型是否能根据反馈调整策略。

④ 构造对比任务集

同一场景生成多个条件略有不同的任务。

例如：

- 某个任务中首选颜色有库存；
- 另一个任务中首选颜色缺货，只能选择原颜色。

如果模型只是死记某种固定操作，很可能无法在所有变体上成功。

### 评估方法

**1. 不检查“过程”，而检查“最终状态”**

系统不要求智能体严格按照作者的参考步骤操作，而是比较：

- 执行任务前的数据库；
- 执行任务后的数据库。

重点检查最终数据库是否发生了正确变化。

例如，购买 T 恤的任务可能检查：

- 是否新增了一个 Amazon 订单；
- 商品类型是否为 T 恤；
- 颜色是否符合要求；
- 尺码是否正确；
- 是否使用了有效支付方式。

只要这些最终条件满足，模型通过哪条路径完成并不重要。

**2. 同时检查附带损害**

系统计算任务前后数据库的差异，检查：

- 新增了哪些记录；
- 修改了哪些记录；
- 删除了哪些记录；
- 哪些字段发生了变化。

评估程序将变化分成两类：

- **必须发生的变化**：例如必须创建正确订单；
- **允许但非必须的变化**：例如购物车下单后保持为空，或者被恢复到原状态。

除此之外出现的变化，都可能被视为误操作。

这种评估比“最终回答看起来正确”更严格，因为它能检测智能体是否偷偷或意外修改了其他数据。

**3. 两个主要评价指标**

TGC：Task Goal Completion

任务目标完成率。

表示所有单个任务中，有多少任务通过了全部评估测试。

例如 TGC 为 40%，意味着 100 个任务中约 40 个被完全正确完成。

SGC：Scenario Goal Completion

场景目标完成率。

只有当模型成功完成一个场景下的所有任务变体时，该场景才算成功。

因此，SGC 比 TGC 更严格，主要评估模型面对不同初始条件时是否稳定、可靠。

### 工作流程

- **生成任务环境**  
  系统从基础数据库出发，为每个任务创建独立的初始状态，包括用户、应用数据、日期时间、干扰信息和现实障碍。
- **给智能体任务指令**  
  例如：“查看室友本月发来的 Venmo 请求，并全部批准。”
- **智能体交互式执行**  
  智能体通过 API 查询应用数据、编写并运行代码，根据返回结果或报错继续调整，直到认为任务完成。
- **记录环境变化**  
  系统比较任务执行前后的数据库，找出新增、修改或删除的内容。
- **自动评估结果**  
  评估程序检查：
  - 是否完成了任务要求；
  - 是否修改了正确的对象；
  - 是否造成了无关或错误的额外操作。



提供了任务、可执行环境、模拟数据和自动评测程序

整个 benchmark 有 750 个任务，划分为 `train`、`dev`、`test_normal` 和 `test_challenge`

**安装环境 → 选择任务 → 接入 Agent → 在 dev 调试 → 冻结配置 → 跑测试集 → 查看 TGC/SGC。**

## 三、实验设计

AppWorld Benchmark 共包含：

- **250 个任务场景**；
- 每个场景 3 个任务；
- 总计 **750 个任务**。

| 数据集    | 任务数 | 用途        |
| ------ | --- | --------- |
| Train  | 105 | 用于示例和开发方法 |
| Dev    | 60  | 调参和方法开发   |
| Test-N | 168 | 普通测试集     |
| Test-C | 417 | 挑战测试集     |

任务复杂度

AppWorld 中，一个任务平均需要：

- 使用约 1.8 个应用，最多 6 个；
- 使用约 9.5 种不同 API，最多 26 种；
- 编写约 50 行代码；
- 最长参考解法超过 130 行；
- 通过多个状态评估测试。

**baseline**

作者测试了六类方法。

① ReAct

模型反复进行：思考 → 编写代码并执行 → 查看结果 → 再思考。

② Plan-and-Execute

模型先制定总体计划，再逐步执行计划中的每一步。

③ Full Code + Reflexion

模型一次生成完整代码。

若执行失败：

- 将错误堆栈返回给模型；
- 模型反思错误；
- 重新生成代码。

④ Iterative Parallel Function Calling

模型每轮生成一批相互独立的 API 调用，同时执行，再根据所有返回结果决定下一轮动作。

⑤ ToolLLaMA

一种专门经过工具调用训练的模型，主要生成连续的 API 调用序列。

⑥ CodeAct

让模型通过代码而不是纯文本动作与工具环境交互，是一种经过专门微调的代码行动智能体。

**测试的基础模型**

前四种方法分别搭配以下模型：

- GPT-4o；
- GPT-4 Turbo；
- LLaMA 3；
- DeepSeek-Coder。

CodeAct 和 ToolLLaMA 使用各自配套的专用模型。

### 实验结果

## 1. 整体表现较低

表现最好的组合是：

> **GPT-4o + ReAct**

其任务完成率为：

- Test-N：TGC 48.8%；
- Test-C：TGC 30.2%。

对应的场景完成率更低：

- Test-N：SGC 32.1%；
- Test-C：SGC 13.0%。

这意味着，即便单个任务偶尔能完成，模型也很难稳定完成同一场景下所有不同变体。

部分主要结果如下：

| 模型与方法             | Test-N TGC | Test-C TGC |
| ----------------- | ---------- | ---------- |
| GPT-4o + ReAct    | 48.8       | 30.2       |
| GPT-4o + PlanExec | 44.6       | 19.7       |
| GPT-4 Turbo 最佳方法  | 32.7       | 17.5       |
| LLaMA 3 最佳方法      | 24.4       | 7.0        |
| DeepSeek 最佳方法     | 13.1       | 5.8        |
| CodeAct           | 0.0        | 0.0        |
| ToolLLaMA         | 0.0        | 0.0        |

因此，论文说明当时较强的大模型仍无法可靠处理复杂的、多应用交互任务。

作者对 GPT-4o 的错误进行了人工分析，发现四类主要问题。

### 常见失败类型

**1.不与环境交互**

模型直接猜测信息，而不是调用应用查询。

例如，它可能凭空猜测室友的电子邮箱地址。

**2. API 理解和使用错误**

例如：

- 编造不存在的参数；
- 读取不存在的返回字段；
- 调用了语义相近但实际错误的 API；
- 混淆“收到的转账请求”和“发出的转账请求”。

**3. 指令执行不完整**

例如，任务要求：

> 只批准本月室友发来的转账请求。

模型却批准了所有请求。

**4. 常识和状态管理错误**

例如：

- 把歌曲加入播放列表的日期误认为发行日期；
- 忘记已经做过的操作；
- 重复查询或重复执行；
- 最终耗尽允许的模型调用次数。

## 四、总结

### 创新点

**把“工具调用评测”变成为“交互式编码评测”**

以前很多 benchmark 主要测试模型能否按顺序调用少量 API；AppWorld 测的是更接近真实 Agent 的能力：

- 先查询环境；
- 根据返回结果继续推理；
- 编写包含循环、条件判断和数据处理的代码；
- 遇到错误后修改策略；
- 跨多个应用完成任务。

**用“最终数据库状态”评测，而不是匹配固定答案路径**

复杂任务通常有多种正确做法，因此论文不要求 Agent 必须按照某个参考步骤执行，而是检查任务前后数据库的变化。

### 不足

**模拟环境与真实世界仍有差距**

虽然数据和 API 设计得较真实，但本质上仍然是封闭的模拟世界：

- API 返回格式较规范；
- 应用种类有限；
- 用户关系和行为由程序生成；
- 不会遇到真实网络波动、验证码、权限弹窗等问题。

**数据规模不足以直接训练大型 Agent**

Benchmark 有 750 个任务、250 个场景，适合评测，但对训练模型来说规模偏小。论文明确表示，由于任务是高质量人工设计的，数据量不足以作为大规模训练集。

### Q&A

**1. 这篇论文主要解决了什么问题？**

这篇论文解决的是现有工具调用 benchmark 过于简单的问题。过去的任务通常只需要按顺序调用少量 API，而真实数字助理需要操作多个应用，根据中间结果继续推理，编写包含循环和条件判断的代码，并处理错误。AppWorld 因此提出了一个更复杂、可交互的 Agent 评测环境。

**2.AppWorld 有标准答案吗？**

有参考解法和评测标准，但并不要求 Agent 完全复制参考操作步骤。作者为任务编写了程序化验证解法，确保任务能够完成；正式评测主要检查任务执行前后数据库的变化。因此，不同 Agent 即使采用不同操作路径，只要最终状态正确，都可以通过。

**3.AppWorld 中的数据是真实数据吗？**

不是现实用户数据，而是模拟生成的数据。作者构造了 106 名虚构用户，为他们设置朋友、家人、室友和同事等关系，并生成邮件、转账、购物和音乐等活动记录。部分要求准确语义的数据由人工编写，部分普通文本由 ChatGPT 辅助生成，最终基础数据库约有 37 万行记录。

**4.任务是怎样生成的？**

作者先设计一个任务场景模板，再通过改变人物、商品、颜色、日期和数据库状态生成多个任务实例。每个任务生成器包含 Setup、Evaluation 和 Validation Solution 三部分，分别负责构建任务环境、定义评测条件和验证任务确实可解。每个场景通常产生三个条件不同的任务变体。
